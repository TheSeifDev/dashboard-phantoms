# Independent Review — Web Projects

**Verdict: not ready for acceptance.** The frontend route and feature-permission gates are present, and the reviewed server helpers generally scope project reads to program admins or active, agreement-accepted project members. However, several protected operations are either too permissive or cannot succeed through the UI, and persisted progress can be presented as zero. Items below are based on the current uncommitted snapshot relative to `a1d063ea390d00179832ef4307044846cca50902`.

**Review boundary:** Read-only inspection of the brief, plan, outcomes, API contract, feature/workspace UI, routing and permission code, and the current pending migration definitions. No browser, tests, or database were run. Migration syntax/manifest work was in progress; findings below rely on the inspected operation, grant, policy, and field definitions, not on applying the migration.

## P1 — Fix before acceptance

1. **Stored JavaScript URL can execute from a task attachment (security).** The authenticated insert policy allows an active project contributor to create an attachment (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:2155-2162`), while the attachment table only requires either a URL or storage path and does not constrain the URL scheme (`:634-648`). The detail view renders `item.external_url` directly as an anchor (`frontend/src/features/web-projects/workspace/TaskDialog.tsx:598-605`). A contributor can submit a `javascript:` URL through the authenticated API and expose it to other project members as a clickable stored link. Validate allowed schemes server-side and render through the existing `safeHref`/`SafeLink` boundary; add a negative authorization/security test.

2. **Viewer role is not read-only for project resource references (server authorization).** The policy grants INSERT when `web_can_access_project(project_id)` is true (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:2202-2209`); that helper includes every active, current-agreement member, including viewers (`:851-870`). Authenticated users have INSERT on the reference table (`:1983-1989`). Thus a viewer can directly add a project-resource link even though the UI hides the control. Require project-lead/program-admin authority in the INSERT policy, consistent with the DELETE policy at `:2210-2211`, and test direct viewer writes.

3. **Deliverable requests and member resubmission cannot complete end-to-end.** The lead UI can request a deliverable for another roster member and submits that member as `submitted_by_member_id` (`frontend/src/features/web-projects/workspace/TasksTab.tsx:126-168`). But INSERT policy only accepts the current member as submitter (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:2087-2094`), so a lead cannot create the requested item for the selected contributor. For edits/resubmission, the UI sends title, description, evidence, dates/links, status and submission time (`TasksTab.tsx:134-149`), but table UPDATE grant only includes status/review columns (`...web_projects_foundation.sql:1993-1994`); the remaining fields are not writable. Provide a narrowly authorized request/update operation (or equivalent row/column policies) and verify leader request, member submission, and revision resubmission.

4. **New-task assignee selections are silently discarded.** `TaskDialog` reads checkbox selections and applies them only inside `if (id && task)` (`frontend/src/features/web-projects/workspace/TaskDialog.tsx:186-215`). For a new task `task` is null, so the task is created but none of the selected assignees are inserted. This breaks the leader create-and-assign workflow and makes the visible assignee choices misleading. Apply selected assignments after the new task ID is returned, then refresh both task and assignee data.

5. **Task-detail attachment, checklist, and subtask controls send invalid operations.** Attachment insertion sends `uploader_member_id` (`frontend/src/features/web-projects/workspace/TaskDialog.tsx:620-639`), but the table/policy field is `uploaded_by_member_id` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:634-648, 2155-2162`), so every link attachment write fails. Checklist insertion omits required `created_by_member_id` (`TaskDialog.tsx:520-540`; table definition `...web_projects_foundation.sql:616-630`), and the UI's completion update from a different assignee fails the policy check requiring the original `created_by_member_id` to match the current member or be lead (`:2146-2154`). Subtask insertion omits required `reporter_member_id` (`TaskDialog.tsx:657-670`; table definition `:548-575`) and is exposed to non-leads even though task INSERT is lead-only (`:2107-2115`). Align payloads, implement the intended creator/updater semantics, and hide or authorize controls by role.

6. **Ordinary blank descriptions prevent task/milestone creation or save.** The task form converts an empty description to `null` (`frontend/src/features/web-projects/workspace/TaskDialog.tsx:133-151`), although `web_project_tasks.description` is `NOT NULL DEFAULT ''` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:548-575`). The timeline similarly sends null for blank `description` and `phase` (`frontend/src/features/web-projects/workspace/TimelineTab.tsx:125-134`) although both milestone columns are `NOT NULL DEFAULT ''` (`...web_projects_foundation.sql:431-446`). These controls are optional in the forms, so normal blank values generate database errors. Send empty strings or omit those columns.

7. **Persisted sprint and milestone progress is read using wrong view fields.** Sprint progress rows expose `sprint_id`, not `id` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:2256-2266`; contract: `WEB_PROJECTS_API_CONTRACT.md:73-79`), but the board builds its lookup map with `p.id` (`frontend/src/features/web-projects/workspace/AgileTab.tsx:55-56`). Every sprint lookup therefore misses and its displayed counts default to zero (`AgileTab.tsx:332-350`). The milestone view exposes `tracked_item_count`, while Overview reads the nonexistent `task_count` (`OverviewTab.tsx:162-174`; migration `:2233-2241`), so milestone progress says there is no tracked work even when records exist. The timeline bar checks `progress_percent` but derives its fill width from nonexistent `completion_percentage` (`TimelineTab.tsx:387-391`). Correct these field names and cover nonzero progress in tests; this is an acceptance blocker for real sprint/milestone progress.

8. **Adding or editing shared PHANTOMS resources aborts in the activity trigger.** A shared `web_resources` row has `project_id IS NULL`, but the activity function falls back to the row's `id` as `v_project_id` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:1117-1120`) and then inserts that value into `web_project_activity_logs` (`:1141-1146`), whose `project_id` must reference a real project (`:765-775`). The capture trigger is installed on `web_resources` (`:1160-1172`). Consequently the shared-library add/edit UI (`frontend/src/features/web-projects/ResourcesPanel.tsx:26-40`) cannot commit a shared resource. Skip project activity capture for projectless shared resources or give them a correctly scoped audit destination.

## P2 — Important correctness and workflow gaps

9. **“Reactivate” membership action is guaranteed to fail.** The UI calls `web_set_project_member_status` with `p_status: 'active'` (`frontend/src/features/web-projects/workspace/PeopleReportsTabs.tsx:227-235`), while the RPC rejects every status except `suspended` and `removed` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:1583-1595`; contract: `WEB_PROJECTS_API_CONTRACT.md:58-61`). The button is a dead control. Implement a reactivation flow that returns the member to pending agreement acceptance, or remove/rename the control and guide the lead through the supported re-invite flow.

10. **Consent UI can show stale opt-in state and overcount consent.** Consent records use `recorded_at` (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:410-423`; contract: `WEB_PROJECTS_API_CONTRACT.md:25-26`), but `TeamTab.currentConsent` sorts by `created_at` (`frontend/src/features/web-projects/workspace/PeopleReportsTabs.tsx:34-44`). The generic query orders by `id` for this table (`frontend/src/features/web-projects/api.ts:65-70`), not by event time. After revoke/re-grant, the checkbox can therefore represent an older event. Settings also counts every historical `granted` row without selecting the latest event (`ResourcesSettingsTabs.tsx:720-731`). The server-side consent gate uses the latest event, which is the right authority, but the user-facing consent record is unreliable; use `recorded_at` and latest-per-member/type semantics.

11. **Blocked/cancelled tasks disappear from the Agile board.** The board renders only `BOARD_STATUSES` (`frontend/src/features/web-projects/workspace/types.ts:82-88`, `AgileTab.tsx:151-154, 385-411`). Its status filter includes `blocked` and `cancelled`, but those tasks still have no rendered column, so filtering to either state produces no visible cards. Add visible treatment/columns or another reachable section for these workflow states.

12. **Project-resource controls and integration choices have additional mismatches.** Project resource creation sends `is_approved: true` (`frontend/src/features/web-projects/workspace/ResourcesSettingsTabs.tsx:69-88`), while the INSERT policy requires `NOT is_approved` for a project-scoped resource (`backend/supabase/migrations/20261120223000_web_projects_foundation.sql:2189-2196`); this makes the project-resource add control fail. The same view offers deletion, but the migration grants no `DELETE` on `web_resources` and defines no resource DELETE policy (`:2008-2010, 2197-2200`). Also the integration selector offers `design` and `product` (`ResourcesSettingsTabs.tsx:497-512`), while the database check allows `figma`/`live_demo` and other values but not those two (`...web_projects_foundation.sql:748-757`). Align the UI with supported operations and enum values.

## Acceptance gaps / lower-priority follow-up

- The settings form does not expose project logo/cover editing, and amendment always submits empty `p_terms: {}` (`frontend/src/features/web-projects/workspace/ResourcesSettingsTabs.tsx:690-711`); these leave required product/consent context only partially manageable. Add them if they are part of the intended initial release rather than treating them as future work.
- Workspace tabs generally do not surface errors/retry for their data queries; failed progress, roster, or activity reads can look like empty/zero data. Add query error states before relying on these values for review.
- No confirmed React hook-order defect or cross-project **read** leak was found in the inspected paths. The route/feature bit is separately guarded and the migration's ordinary project reads use membership/agreement-scoped helpers. This does not waive the confirmed viewer write-policy issue above.
- File upload/storage provider configuration remains a known limitation in the brief; the UI labels links-only behavior. It is not counted as a newly discovered defect here.
