### 2.2 تحليل الثغرة الأمنية CVE-2026-78206 (Data Amplification / Zip Bomb)
- **التصنيف:** CWE-409 (Improper Handling of Highly Compressed Data / Decompression Bomb).
- **الخطورة:** متوسطة إلى عالية (تعتمد على سياق التشغيل؛ تسبب حجب الخدمة DoS واستهلاك الذاكرة).
- **طبيعة الثغرة:** تستخدم ملفات XLSX صيغة أرشيف ZIP مضغوطة بواسطة خوارزمية Deflate. عند قراءة الملف، يقوم `exceljs` بفك ضغط ملفات XML الداخلية (`xl/worksheets/sheet1.xml`، `xl/sharedStrings.xml`) في الذاكرة دون تطبيق قيود مسبقة على حجم البيانات بعد فك الضغط أو نسبة التضخيم (Decompression Ratio).
- **النتيجة المحتملة:** ملف Excel بحجم 50 كيلوبايت يمكن أن يتمدد إلى 5 جيجابايت في الذاكرة، مما يؤدي إلى:
  - تجميد متصفح العميل (Browser Tab Crash / Out of Memory) في الواجهة الأمامية.
  - انهيار خادم Node.js في حالة استخدامه في الخلفية.

   - ❌ لا يوجد حد أقصى لعدد الإدخالات داخل الأرشيف (Entry Count Cap - مثل منع تجاوز 500 ملف داخلي).

### 2.6 التوصية الهندسية الصارمة لمعالجة الجداول
1. **حذف فوري من الـ Bridge:** إزالة `exceljs` تماماً من `backend/whatsapp-bridge/package.json` لأنها تبعية ميتة.
2. **عدم التراجع التلقائي لـ `xlsx` غير الموثق:** تجنب العودة للنسخ القديمة من `xlsx` أو الاعتماد على مستودعات غير معتمدة مؤسسياً.
3. **تطبيق درع فحص ZIP مسبق (Pre-Decompression Defensive Wrapper):**
   - فحص حجم الملف قبل القراءة (بحد أقصى 5 ميجابايت لملفات استيراد الأعضاء).
   - قراءة ترويسة الـ Central Directory لأرشيف الـ ZIP عبر مكتبة فحص خفيفة ومحدثة (مثل `fflate`).
   - جمع إجمالي الحجم غير المضغوط `uncompressedSize` لكل إدخال والتأكد من أنه لا يتجاوز 25 ميجابايت.
   - حساب نسبة الضغط الإجمالية `(uncompressed / compressed)` والتأكد من أنها لا تتجاوز `50:1`.
   - في حال تجاوز أي حد، يتم رفض الملف فوراً وتنبيه المستخدم دون تمرير الـ Buffer إلى `exceljs`.
4. **العزل في Web Worker:** نقل عمليات قراءة وتوليد ملفات Excel إلى Web Worker لمنع أي تجميد لواجهة المستخدم.

## 6. مراجعة مصادقة الأعضاء والجلسات (Member Authentication & OTP Review)

تم فحص التفاعل بين كود الواجهة الأمامية في [`frontend/src/features/auth/LoginPage.tsx`](file:///C:/projects/phantoms/dashboard/frontend/src/features/auth/LoginPage.tsx#L56-L165) وإجراءات قاعدة البيانات المحصنة في [`backend/migrations/0022_dynamic_system_ownership.sql`](file:///C:/projects/phantoms/dashboard/backend/migrations/0022_dynamic_system_ownership.sql#L230-L365).

### 6.1 تدفق المصادقة عبر OTP وربط الأجهزة
1. يدخل العضو بريده الإلكتروني.
2. إذا كان الجهاز مرتبطاً وموثقاً سابقاً في جدول `member_device_sessions` خلال آخر 90 يوماً، يتم التحقق منه مباشرة عبر استدعاء `lookup_member_by_email` برمز الجهاز المشفر.
3. إذا كان الجهاز جديداً، يتم طلب رمز OTP عبر البريد عبر `supabase.auth.signInWithOtp`.
4. بعد إدخال الرمز بنجاح والتحقق عبر `supabase.auth.verifyOtp`، يصبح لدى العميل توثيق ساري (`auth.jwt() ->> 'email'`).
5. يتم استدعاء `bind_member_device_session` التي تتحقق من تطابق بريد العضو مع الـ JWT الموثق، ثم تسجل رمز جهاز جديد مشفر بـ SHA-256.

### 6.2 رصد تعارض معماري ومسار ميت (Dead/Misleading Fallback Path)
في كود `LoginPage.tsx` (الأسطر 100-111):
```typescript
if (otpError) {
  // If Supabase Auth is not configured for OTP, fall back to lookup_member_by_email
  const fallbackToken = generateDeviceToken();
  const member = await fetchMemberByEmail(cleanEmail, fallbackToken);
  if (!member) {
    setError('البريد ده مش مسجل في فريق وصلة. راجع الإدارة.');
  } else {
    // login user...
  }
}
```
**التحليل الجنائي للتعارض:**
1. أراد كاتب كود الواجهة إنشاء مسار بديل في حال تعطل خدمة OTP أو عدم إعدادها، يسمح بتسجيل الدخول التلقائي.
2. لكن الهجرة `0022_dynamic_system_ownership.sql` (الأسطر 342-354) قامت **بتصليب أمني صارم ومحكم لمنع انتحال الهوية (SEC-CRIT-02)**، حيث تشترط الدالة `lookup_member_by_email`:
   ```sql
   IF (v_caller_email <> '' AND v_caller_email = pg_catalog.lower(pg_catalog.btrim(p_email))) OR public.is_admin() THEN
     -- bind device
   END IF;
   IF v_is_bound OR public.is_admin() THEN
     RETURN QUERY SELECT ...
   END IF;
   ```
3. نظراً لأن المتصل في حالة فشل OTP هو متصل مجهول (`anon`) لا يملك JWT موثقاً ولم يسبق ربط جهازه، فإن الدالة **لن تُرجع أي بيانات على الإطلاق**.
4. نتيجة لذلك: يعتقد كود الواجهة أن العضو غير مسجل ويطبع رسالة مضللة للمستخدم: `"البريد ده مش مسجل في فريق وصلة. راجع الإدارة."` حتى لو كان بريده مسجلاً بالفعل!
5. **الحكم:** التصليب في قاعدة البيانات سليم أمنياً ويمنع الاختراق، ولكن كود الواجهة الأمامية يحمل مساراً مضللاً يجب تنقيحه ليعلن صراحة أن تسجيل الدخول يتطلب رمز التحقق ولا يمكن تجاوزه.

## 7. ملكية النظام وهجرة قاعدة البيانات (System Ownership & Migrations)

### 7.1 تحرير المعرف الثابت (Dynamic System Ownership)
- **الإنجاز المحقق:** تم إلغاء ربط صلاحيات مالك النظام بالمعرف الثابت السابق (`8ce17aae-84c1-4c89-a020-8b683a0dbabb`) الذي تم رصده في التدقيق الأولي.
- **الآلية الحالية في الهجرة `0022`:**
  - دالة `public.is_owner()` تستعلم جدول `public.admin_accounts` ديناميكياً للتحقق من أن `auth.uid()` يمتلك الدور `role = 'owner'`.
  - دوال `is_admin()` و `has_admin_permission(TEXT)` تمنح المالك كافة الصلاحيات تلقائياً وتمنح المشرفين الآخرين الصلاحيات المحددة في مصفوفة JSONB الخاصة بهم.
  - تم وضع قيود صارمة تمنع تعديل صلاحيات المالك عبر استدعاءات RPC (`OWNER_IMMUTABLE`).

### 7.2 تقييم مخاطر التراجع وقابلية التكرار (Idempotency & Rollback)
- دوال الهجرة `0022` مكتوبة بصيغة `CREATE OR REPLACE FUNCTION` ومحاطة بـ `BEGIN ... COMMIT`، مما يجعلها متكررة وقابلة للتطبيق دون كسر البيئة الحالية.
- **ملاحظة تشغيلية:** عند تطبيق الهجرة على بيئة جديدة تماماً (Fresh Database)، يجب التأكد من وجود مستخدم أولي يمتلك دور `owner` في جدول `admin_accounts` (عبر Seed Script مخصص)، وإلا فلن يتمكن أي حساب من ممارسة صلاحيات المالك.
